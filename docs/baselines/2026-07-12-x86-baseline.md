## Purpose

This document records the reproducible state observed before Phase 1 build-system changes. It is evidence, not a claim that the current compiler or runtime is production-safe.

## Parallel Build Regression Evidence

Command:

```powershell
cmake --build out/baseline-vs2022 --config Debug --target dbp_tests --parallel 8 -- /m:8 /clp:ErrorsOnly
```

Result: failed with exit code `1`.

MSVC reported `C1041` for concurrent writes to:

```text
out/baseline-vs2022/bin/Debug/dbp_compiler_lib.pdb
```

The error occurred across many translation units in `dbp_compiler_lib` and explicitly recommends `/FS`. A follow-up serialized invocation remained blocked because the failed compiler processes/PDB server retained the same PDB. The baseline test executable was therefore not regenerated inside this isolated worktree before the build-policy fix.

This is the RED regression evidence for target-scoped parallel-PDB handling. The fix must be verified with repeated clean parallel builds, not only with a serialized build.

## CTest Discovery Regression Evidence

Command:

```powershell
ctest --test-dir out/baseline-vs2022 -C Debug --show-only
```

Result:

```text
Total Tests: 0
```

CTest returned success despite discovering no tests. The root CMake project creates `dbp_tests` but does not enable/register tests. This is the RED regression evidence for CTest integration.

## Baseline Limitations

- Clean parallel build fails.
- CTest discovers zero tests.
- The isolated clean test executable has not yet been produced.
- DirectX SDK discovery is environment/path dependent.
- Dependencies are downloaded during configure and are not reproducibly pinned.
- Build flags are directory-global and leak legacy settings into third-party code.
- No shared CMake presets or Windows CI workflow exist.
- FPS Creator Classic compatibility has not yet been executed or measured.
- This baseline does not validate Unicode completeness, x64, CLI correctness, VFS safety, AST parity, runtime plugins, or rendering.

## Phase 1 Verified After-State

Verification was completed on 2026-07-12 from the isolated
`codex/modernization-foundation` worktree.

The shared `windows-x86-debug` preset performed a fresh configure and an
eight-job build of `DBPCompiler`, `DarkEXE`, and `dbp_tests`. The build exited
successfully and CTest discovered and passed 36 of 36 tests in 2.03 seconds.
Two earlier consecutive clean parallel test builds also exited successfully,
with no recurrence of `C1041`.

The new `windows-x86-asan` preset instruments project code and its statically
linked test dependencies with MSVC AddressSanitizer. Its first complete run
found a real overlapping `strcpy` in `CStr::SetText`, reached from
`CStr::MakeUpper`. A regression test reproduced the failure before the fix.
After replacing the overlapping copy with defined `memmove` semantics and
making uppercase conversion operate in place, CTest passed 36 of 36 tests
under AddressSanitizer in 5.27 seconds. Leak detection is disabled because the
MSVC x86 AddressSanitizer runtime does not provide a reliable leak-sanitizer
gate; bounds, use-after-free, and overlap checks remain enabled and fatal.

Dependencies are pinned to immutable revisions: spdlog 1.17.0 at
`79524ddd08a4ec981b7fea76afd08ee05f83755d` and GoogleTest 1.17.0 at
`52eb8108c5bdec04579160ae17225d66034bd723`. Legacy compiler switches are
target-scoped and do not propagate into either dependency. C/C++ options are
also language-scoped so MASM no longer receives incompatible compiler flags.

The Windows workflow parses as valid YAML and uses the same Debug and
AddressSanitizer presets in a fail-independent matrix. It downloads the pinned
Microsoft D3DX compatibility package and verifies SHA-256 before configuration.
`git diff --check` reports no whitespace errors, and no generated `.sbr`,
`.pdb`, `.obj`, `.ilk`, or `.tlog` file is tracked.

Warnings remain in legacy production code, notably ANSI/wide-character
mismatches in the icon and VFS paths, narrowing conversions, the required but
deprecated `/Zc:forScope-` compatibility switch, and unused parameters. They
are recorded debt for focused TDD migrations; suppressing them globally would
hide compatibility and Unicode defects.

FPS Creator Classic was inventoried but was not built during this foundation
phase. This phase therefore makes no claim of FPS Creator project compatibility
and no claim of completed Unicode, x64, renderer, plugin, VFS, AST, or CLI
modernization.
