# Design — int64 (type 9) arithmetic becomes full-width REG64 (no DLL calls)

Date: 2026-08-12
Wave: 8b (closes the int64 deferral recorded in wave 8: "بقيت R/int64 وPower/Mod DLL")

## 1. Problem

`double integer` (int64, type 9) is the **last arithmetic type whose operations
still route through runtime DLL calls**. `a=b+c` for two int64 variables emits:

1. Two 32-bit half loads (`MOVEAXMEM4 [b+4]` → EDX, `MOVEAXMEM4 [b]` → EAX);
2. Both halves pushed (`PUSH EDX; PUSH EAX`);
3. `WriteASMCall` → `?AddRRR@@YA_J_J0@Z` (dbprocore.dll);
4. The x64 call-frame stub reassembles the two slots with `SHL RCX,32 / OR RAX,RCX`;
5. The result comes back in EDX:EAX and is stored as two 4-byte halves.

The hardcoded math path in `CASMWriter::WriteASMTaskCore` still rejects type 9
with `ERR_SYNTAX+50` ("cannot hard code strings and doubles (yet)"), and
`CTaskEmitter::DetermineASMCall` maps type 9 to the 4-byte size ladder.

## 2. Target semantics

All type-9 loads/stores and the five integer math families become **full-width
REG64** emitted inline by the assembler:

| Operation | Old (DLL) | New (REG64) |
|---|---|---|
| add | `?AddRRR` call | `48 01 D8` ADD RAX,RBX |
| sub | `?SubRRR` call | `48 29 D8` SUB RAX,RBX |
| mul | `?MulRRR` call | `48 0F AF D8` IMUL RAX,RBX |
| div | `?DivRRR` call | `48 99` CQO + `48 F7 FB` IDIV RBX |
| mod | `?DivRRR`+half-swap (not registered) | CQO + IDIV + `48 8B C2` MOV RAX,RDX |
| compare | `?EqualLRR`/`?GreaterLRR`/... | `48 3B DA` CMP RDX,RBX + SETcc |
| load | two 4-byte halves | single 8-byte (`MOVEAXMEM8` etc.) |
| store | two 4-byte halves | single 8-byte (`MOVMEMEAX8` etc.) |

Comparisons keep the existing int flow shape (`MOV EDX,[b]` … `CMP EDX,EBX` +
SETcc) but widened to 64-bit registers.

**Value layout**: int64 slots remain little-endian `[low dword @ offset,
high dword @ offset+4]` in varspace — the same layout the 8-byte `MOVEAXMEM8`
moffs64 form reads/writes, so no data-format change is needed.

## 3. Registration changes (InstructionTable.cpp)

The six RRR math commands move from `AddCommandCore` (BuildID 0 → DLL path) to
`AddBuildCommand` (hardcoded path) with their existing `InternalInstruction`
IDs:

- `?AddRRR` → `AddRRR` / `BuildTask::Add`
- `?SubRRR` → `SubRRR` / `BuildTask::Sub`
- `?MulRRR` → `MulRRR` / `BuildTask::Mul`
- `?DivRRR` → `DivRRR` / `BuildTask::Div`
- `?EqualLRR` / `?GreaterLRR` / `?LessLRR` / `?NotEqualLRR` /
  `?GreaterEqualLRR` / `?LessEqualRR` → the six `BuildTask::Equal…LessEqual`
  values (same pattern as the `CONDLLL` block, but "RR" param types).

`PowerRRR` stays a DLL call (consistent with `PowerLLL`, which is also DLL —
power has no single-instruction encoding and is a library routine).

Mod: there is no `ModRRR` entry today; `case 6` falls through to the
type-agnostic switch and returns 0. We add `ModRRR` with `BuildTask::Mod`
alongside Div so `a mod b` on int64 becomes native IDIV remainder.

## 4. New ASMOp codes + DefineASM table entries

All 8-byte forms carry `OpcodeExpansion::RexW`:

| ASMOp | Bytes | Meaning |
|---|---|---|
| `ADDEAXEBX8` | 48 01 D8 | ADD RAX,RBX |
| `SUBEAXEBX8` | 48 29 D8 | SUB RAX,RBX |
| `MULEAXEBX8` | 48 0F AF D8 | IMUL RAX,RBX |
| `DIVEAXEBX8` | 48 F7 FB | IDIV RBX |
| `CQO` | 48 99 | sign-extend RAX into RDX:RAX |
| `MOVEAXEDX8` | 48 8B C2 | MOV RAX,RDX (mod remainder) |
| `MOVEBXRAX8` | 48 8B D8 | MOV RBX,RAX |
| `CMPEDXEBX8` | 48 3B DA | CMP RDX,RBX |

Existing 8-byte load/store opcodes are reused: `MOVEAXMEM8`, `MOVMEMEAX8`,
`MOVEAXEBP8`, `MOVEBPEAX8`, `MOVEAXECXOFF8`, `MOVECXOFFEAX8`, `MOVEAXECXREL8`,
`MOVEAXEAXREL8`, `MOVEAXSIB8`, `MOVECXEAXOFF8`, `MOVEAXECX8`, `MOVEAXOFFECX8`.

## 5. Emitter changes

### 5.1 TaskEmitter — type-9 load/store to single 8-byte moves

`WriteASMXtoEAX` (load) and `WriteASMEAXtoX` (store) currently special-case
`case 9` with the two-half EDX:EAX dance in Mem/MemOff/Ebp/EbpOff. Each becomes
one 8-byte move:

- Mem: `MOVEAXMEM8` / `MOVMEMEAX8`
- MemOff: `MOVEAXECXOFF8` / `MOVECXOFFEAX8`
- Ebp: `MOVEAXEBP8` / `MOVEBPEAX8`
- EbpOff: `MOVEAXEBP8` / `MOVEBPEAX8` (offset forms)
- MemArr/EbpArr: the array-element value read/write already goes through
  `MOVEAXSIB8`; the final element access widens from `MOVECXEAXOFF4`/`MOVECXEAX8`
  (`WriteASMARRtoEAX`/`WriteASMEAXtoARR` `case 9`).
- Stack: `PUSHEDX;PUSHEAX` pair becomes `PUSHEAX` (a single 8-byte push of the
  full value) — **this is the int64 DLL-arg ABI on x64**: the value rides one
  8-byte stack slot, matching `IsDoubleSlotType` semantics. EmitX64CallFrame
  already handles type 9 as a 2-slot type; we keep that so user DLLs receive
  the same value as before, but the producer side is now one move instead of two.

`DetermineASMCall`: type 9 joins the pointer-family 8-byte special case? No —
**int64 is a value type, not a pointer**. The two-half producers above are
replaced by explicit single-move emission, and the size ladder keeps type 9 at
size-code 3 (DWORDx2) for the (now unused) fallback paths. The explicit
`case 9` blocks are the contract.

### 5.2 ASMWriter — int64 math/compare branches

In `WriteASMTaskCore`, before the `dwP1Type==3||8||9` rejection:

```
const bool bInt64Math = (dwP1Type==9 || dwP1Type==109)
    && task in {Add,Sub,Mul,Div,Mod};
```

- P2 → `WriteASMXtoEAX` (now 8-byte) then `MOVEBXRAX8` (RBX holds B);
- P1 → `WriteASMXtoEAX` (RAX holds A);
- Div/Mod guard: `CMPEBX4 0` / `JNE 15` / error 119 / `JMP 3` — same shape as
  the int path (CMP EBX,0 is fine: zero is zero in any width);
- Add/Sub/Mul: the three new opcodes;
- Div: `CQO` + `DIVEAXEBX8`; Mod: same + `MOVEAXEDX8`;
- P3 → `WriteASMEAXtoX` (8-byte store).

Compare branch: `bInt64Compare = (dwP1Type==9||dwP1Type==109) && task in
{Equal…LessEqual}` → `WriteASMXtoEAX(P2)` → `MOVEBXRAX8`; `WriteASMXtoEAX(P1)`
→ `CMPEDXEBX8` + existing SETcc block.

The DLL-arg path for type 9 (user DLLs with int64 params) flips to the
correct MS x64 ABI: `__int64` rides a single integer register. TDD discovery:
keeping the old two-4-byte-half push (`PUSHEDX;PUSHEAX`) with the new 8-byte
loads would push garbage in EDX, so `WriteASMEAXtoX(Stack)` case 9 emits one
`PUSHEAX` (8 bytes) and `IsDoubleSlotType` drops 9/109 (only doubles 8/108
stay two-slot). `EmitX64CallFrame` then moves the arg straight into
RCX/RDX/R8/R9 — the reassembly branch is gone for int64.

## 6. Conversions

The int↔int64 casts (`?CastLtoR@@YA_JH@Z`, `?CastRtoL@@YAK_J@Z`) remain DLL —
they are *conversions*, not arithmetic; the user-facing `dim a as double
integer` flow first casts then does REG64 math, and the cast DLL already
returns a full 64-bit RAX. Converting them is a separate, optional wave. The
`?Cast*toR`/`?CastRto*` family is intentionally left for that wave.
