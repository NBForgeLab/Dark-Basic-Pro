# Plan — Wave 21: Native float modulo (ModFFF via CRT fmod)

## Mission

Replace the last scalar-arithmetic dbprocore.dll row — `?ModFFF@@YAKMM@Z`
(float `mod`) — with an emitter-built CRT `fmod` call following the wave-17
exp/log pattern (msvcrt.dll resolved through the command table) — TDD.

## Context

Verified in DBDLLCore.cpp: `ModFFF(float a, float b)` is
`if(b==0) return 0; float(fmod((double)a,(double)b))`. So the emitter must
widen both operands to double, call `fmod(double,double)` (two XMM arguments
per the x64 ABI — unlike the one-argument exp/log), narrow the result back
to float, and return 0.0f for a zero divisor. The zero test must match C
semantics: `+0.0` and `-0.0` are both zero (return 0), but a NaN divisor is
`!= 0` and must still reach fmod (→ NaN). A sign-stripped bit test
(`AND EAX,0x7FFFFFFF; JNE ...`) is exact for every real float.

## TDD discoveries

1. **`EmitAlignedCrtCall` extraction** — the wave-17 one-argument exp/log
   call and the new two-argument fmod call share the pad/frame, msvcrt
   resolution, and SUB/ADD restore; the refactor kept every wave-17 Power
   test green.
2. **The guard bytes are little-endian** — the first test draft asserted
   `25 7F FF FF FF` (big-endian reading) while the emitter correctly writes
   `25 FF FF FF 7F` for 0x7FFFFFFF; the byte dump proved the implementation
   right and the expectation wrong.
3. **Sign-stripped bit test matches C exactly** — `AND EAX,0x7FFFFFFF`
   covers `+0.0` and `-0.0` (both `== 0` in C) while NaN mantissa bits keep
   NaN divisors flowing to fmod — unlike a UCOMISD compare whose unordered
   flags would collapse NaN into the zero path.
